# TGproxycheck

Моя программа для проверки прокси Telegram. Поддерживает как MTProto, так и SOCKS5. Проверка SNI для российских белых списков и многое другое.

**Вкратце почему она многоуровневая и как вообще ВСЁ работает:**

__1. Проверка ссылки:__

Сначала программа разбирает Telegram-ссылку и проверяет её структуру.

Поддерживаются:

tg://proxy?server=...&port=...&secret=...
https://t.me/proxy?server=...&port=...&secret=...

tg://socks?server=...&port=...
https://t.me/socks?server=...&port=...

Проверяются адрес сервера, порт и необходимые параметры прокси.

__2. Проверка MTProto Secret__

Для MTProto определяется тип секрета:

| Тип            | Что означает                                    |
|----------------|-------------------------------------------------|
| Standard       | обычная MTProto-обфускация                      |
| dd / Padded    | MTProto с дополнением пакетов                   |
| ee / Fake-TLS  | маскировка соединения под TLS/HTTPS             |

Программа проверяет HEX-формат секрета, его длину и возможность декодирования.

Для обычного и dd-секрета ожидается 16-байтный ключ.

У Fake-TLS дополнительно извлекается и проверяется SNI-домен.

__3. Фильтрация подозрительных SNI__

Для Fake-TLS анализируется домен, зашитый в secret.

Программа умеет отдельно определять:

- SNI, похожие на российские сервисы;
- SNI из внутреннего списка совместимости;
- явно нежелательные или заблокированные домены;
- некорректные Fake-TLS секреты без нормального SNI.

__4. DNS-проверка__

Если вместо IP указан домен, программа пытается преобразовать его в реальный IP-адрес.

Поддерживаются IPv4 и IPv6; при наличии нескольких адресов предпочтение отдаётся IPv4.

Результаты DNS кешируются, поэтому при массовой проверке один и тот же hostname не приходится разрешать заново сотни раз.

__5. Ping и Jitter__

Задержка измеряется не через системную команду ping и не через ICMP.

Программа три раза открывает TCP-соединение с портом прокси и измеряет время установки соединения.

Из этих измерений получаются:

Ping — среднее время подключения.

Jitter — разница между самым быстрым и самым медленным результатом.

Пример:

42 ms / jitter 4 ms

__6. Дополнительная TCP / TLS / HTTP-проба__

Полная проверка выполняет ещё несколько низкоуровневых тестов.

Фиксируются:

| Тест           | Что показывает                                     |
|----------------|----------------------------------------------------|
| TCP Connect    | удалось ли вообще установить соединение            |
| TCP Latency    | время установки TCP                                |
| TLS Probe      | отвечает ли сервер на TLS-подобное начало соединения |
| HTTP Probe     | отвечает ли порт на обычный HTTP HEAD              |
| Response Time  | общее время этой серии тестов                      |

__7. Настоящая MTProto-проверка__

Реальная проверка Telegram-прокси.

Для Standard и Padded программа создаёт MTProto obfuscated transport, шифрует соединение через AES-CTR и отправляет настоящий MTProto-запрос req_pq.

Ответ не принимается на веру.

Проверяются структура MTProto-сообщения, его длина, конструктор ответа и совпадение nonce.

Успешный результат выглядит примерно так:

resPQ получен (84.7 мс)

__8. Проверка настоящего подключения Telegram__

После низкоуровневого MTProto-теста программа выполняет ещё одну независимую проверку через Telethon.

Создаётся Telegram-клиент и выполняется реальная попытка установить соединение через проверяемый прокси.

Причём is_connected() недостаточно.

После соединения дополнительно проверяется наличие созданного auth_key.

То есть TCP-сокет, который просто согласился принять соединение, не должен случайно получить статус рабочего Telegram-прокси.

__9. Несколько клиентских профилей__

Полная проверка запускает несколько Telethon-тестов параллельно.

Используются группы профилей:

MTS
Beeline
Megafon
Tele2

Каждый профиль содержит свой набор параметров клиента: модель устройства, версию системы, версию Telegram и другие данные.

Здесь есть важная оговорка.

**Это не настоящая проверка прокси из физических сетей МТС, Билайн, Мегафон и Tele2.**

Программа не переносит соединение в сеть конкретного мобильного оператора. Это несколько различных клиентских профилей подключения, используемых как дополнительный независимый тест Telethon.

Поэтому корректнее воспринимать результат как:

Telegram connection profiles: 3/4 passed

__10. Геолокация IP__

После получения IP программа пытается собрать информацию о сервере.

В результат могут попасть:

- Страна
- Регион
- Город
- Почтовый индекс
- ISP
- Организация
- ASN
- Часовой пояс
- Координаты
- Хостинг
- Флаг прокси
- Флаг мобильного оператора

Используются несколько GeoIP API с fallback-механизмом и кешированием.

__11. SNI / IP / whitelist-анализ__

Для MTProto-прокси выполняется отдельная эвристическая оценка совместимости IP и Fake-TLS SNI.

Учитываются:

- диапазоны IP Telegram
- известные российские CIDR
- страна IP
- ASN
- SNI Fake-TLS
- внутренний список совместимых доменов
- доступность TCP/443

В зависимости от комбинации программа может выдать, например:

В БС
Вероятно в БС
Частично БС
SNI из списка, но IP не белый
Не в БС

Эту проверку следует воспринимать как эвристику, а не как математическую гарантию обхода блокировок.

__12. Connection Score__

После полной проверки рабочему прокси присваивается рейтинг до 100 баллов.

Для MTProto учитываются:

| Условие                                   | Баллы |
|-------------------------------------------|-------|
| TCP-порт открыт                           | +20   |
| MTProto-тест успешен                      | +15   |
| Telethon подключился                      | +20   |
| Ping < 80 мс                              | +20   |
| Ping < 150 мс                             | +15   |
| Ping < 300 мс                             | +10   |
| Ping < 500 мс                             | +5    |
| Эвристика белого списка/БС успешна        | +15   |
| Подходящий российский SNI                 | +10   |

Максимум:

100 / 100

И многое другое. Можете сами почитать в исходном коде программы. Он достаточно объёмный.
